# At-risk commit ledger — upstream/main integration

Every fork-only commit whose work was discarded by resolving a merge conflict to
the upstream side, and what happens to it now.

This file answers one question for a reader who has no memory of the merge:
**for each of these commits, do we still own the fix, did upstream take it, or
did we let it go?** Read `delta.md` for the file-level view and
[the merge commit](#reproduce) for how to re-derive both.

## How this was computed

Integration baseline: `386e4fd4e` (origin/Paseo-hub) merged with `97083dd73`
(upstream/main), merge commit `921702068`. 119 conflicted paths, all resolved to
upstream.

Two sets, recomputed from scratch against that merged tree rather than reused
from the pre-merge baseline:

| Set | Count | Definition |
| --- | --- | --- |
| dropped fork delta | 184 files | the fork changed the path off the merge base, and after the merge `HEAD:<path>` is byte-identical to `97083dd73:<path>` |
| at-risk commits | 147 | `git log --cherry-pick --right-only 97083dd73...HEAD` (no upstream patch-equivalent), restricted to commits touching at least one of those 184 paths |

Both figures reproduce exactly against the merged tree, and both match the
figures computed before the merge against `5c2c85ebc`. `--cherry-pick` is what
keeps the commit set honest: a fork commit that upstream already carries as a
patch-equivalent is not at risk and does not appear here.

## Classes

| Class | Meaning |
| --- | --- |
| **SUPERSEDED** | upstream independently carries the same change. The upstream sha is cited. |
| **RE-APPLIED** | the fix is not in the tree today and has to be put back. The file to re-apply to is named. |
| **DROPPED-ON-PURPOSE** | the loss is accepted. The reason is stated. |

Two batch rules cover the mechanical commits, and they are the only rules used
without per-commit inspection:

- **V1 version stamping** — commits whose only effect on a dropped path is
  workspace version stamping are DROPPED-ON-PURPOSE. The stamping is regenerated
  by `scripts/sync-workspace-versions.mjs` and carries no runtime behaviour.
- **V2 docs-only** — commits whose dropped paths are all markdown are
  DROPPED-ON-PURPOSE, except `741718dac`, which is fork runbook content with no
  upstream counterpart and is therefore RE-APPLIED.

Everything touching runtime, deploy, CI or a provider was classified
individually against the merged tree.

## Honest gaps

- The 5 SUPERSEDED rows carry 3 tree-state arguments and 2 sha citations. Only
  `eeb0c6056` cites a sha that carries the identical change (`37156b5b8`). For
  `18e79e0b4` and `b0d1cb7f2` the argument is that upstream ships no `bun.lock`
  and installs with npm, which is a property of the upstream tree rather than a
  single commit; no sha is claimed because none is honest.
- `e095e4c82` cites `c3e1e084a` as the last upstream commit touching
  `cache: "npm"` in `ci.yml`. That sha is real and an ancestor of the target,
  but its subject line is about watcher work — it is cited for the string, not
  because it is the semantic origin of npm-based CI.
- The 106 RE-APPLIED rows are individually evidenced, but "re-apply required" is
  a statement about intent, not a verified re-application. Nothing in this table
  has been re-applied yet except the `ci.yml` branch lists (`bdad61141`).
